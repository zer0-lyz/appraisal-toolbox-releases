# 设备价格指数更新（PPI）

## 这个技能解决什么

资产评估底稿里有一张「全年(更新此表数据）」表，存放 10 个分行业设备价格指数
（工业生产者出厂价格指数）月度序列，是「价格指数1」表换算年度重置价指数的数据源。
这些数据需要**每月跟进更新**，手工从统计局网站复制粘贴既慢又容易漏月份。

## 核心策略：基线 + 增量（不要每次全量重抓）

全量抓取要遍历目录树 + 请求 4 个时间分片 × 10 个指标，上百次请求，**1~2 分钟**
且容易触发 NBS 限流。但**历史值几乎不会变**，没必要每次重抓。

所以数据分两层存：

| 层 | 位置 | 内容 | 更新频率 |
|---|---|---|---|
| **基线** | `data/ppi_baseline.json` | 已抓取的 NBS 全量序列 + 底稿现有值快照 | 建立一次，之后只增量合并 |
| 增量 | `_out/nbs_ppi.json` | 仅最近几期 | 每月一次（约 20 秒） |

**技能包自带一份初始基线**（`references/ppi_baseline.json`，10 个序列 /
**1,939 个数据点**，截至 2026-08），所以**新环境开箱即用、不必先全量抓取**：

```bash
# 新环境第一步（几秒完成，不发任何网络请求）
python scripts/ppi_baseline.py --build     # 自动以包内基线打底
```

`--build` 的取数顺序是「**包内基线打底 → 本次抓取结果覆盖 → 写成本地基线**」，
所以即使只抓到最近几期，历史序列也是完整的。

- **日常**：`nbs_ppi.py --recent 6` 只抓最近 6 期（复用缓存的 cid/indicatorId，
  跳过目录树遍历，**实测 21.6 秒**）
- 下游脚本（`verify_ppi.py` / `apply_ppi_to_draft.py`）**自动合并「基线 + 增量」**，
  既能拿到完整历史，又能吃到最新月份
- 只有**包内基线缺的目标列**、或需要长期回补时才跑全量（`nbs_ppi.py`，1~2 分钟）

> 增量抓完记得 `ppi_baseline.py --merge` 把新数据并入基线，
> 否则基线会越来越旧（不 merge 也能跑，但下次换脚本读时就少了这几期）。

定期回看几期还有第二个用处：**校验 NBS 有没有修正历史值**——
`--merge` 会报告"新增 N 期 / 修正历史值 N 期"。

## 关键事实：NBS 新版接口（老接口已废弃）

> ⚠️ **`easyquery.htm` 已于 2026-05 废弃，现返回 403。**
> 网上多数教程仍在讲老接口，照抄必然失败。

**基础地址**：`https://data.stats.gov.cn/dg/website/publicrelease/web/external`

三步走：

| 步 | 接口 | 方法 | 用途 |
|---|---|---|---|
| 1 | `/new/queryIndexTreeAsync?pid=&code=1` | GET | 目录树，`code=1` 为月度数据 |
| 2 | `/new/queryIndicatorsByCid?cid=<cid>` | GET | 数据集下的指标列表 |
| 3 | **`/stream/esData`** | POST | 取数 |

**端点名会变**。文档常写 `/getEsDataByCidAndDt`，但该路径实测 **404**；
当前（2026-09 实测）有效的是 **`/stream/esData`**。
若将来再 404，可设环境变量或改 `nbs_ppi.py` 里的路径常量。

**时间分片**：同一指标按 5 年切成多个 cid，必须分别请求后本地拼接：

```
分行业工业生产者出厂价格指数 (上年同月=100)
   ├─ (2007-2013)      cid 8c707b6d…
   ├─ (2014-2017)      cid 8c1e3ad3…
   ├─ (2018-2025)      cid a9a6bab4…
   └─ (2026-)          cid 8bc27b5f…
```

**indicatorId 跨分片不稳定**，每个 cid 都要重新调 `queryIndicatorsByCid` 取映射。

**取数时间范围要按各分片自身边界传**。统一传全范围会漏数——
实测 2007-2013 分片传全范围只回 48 条，按其边界传可得 84 条。

**月度数据根节点**：`fc982599aa684be7969d7b90b1bd0e84`

**取数请求体**：

```json
{"cid":"...", "indicatorIds":["..."],
 "das":[{"text":"全国","value":"000000000000"}],
 "dts":["201801MM-202512MM"], "showType":"1",
 "rootId":"fc982599aa684be7969d7b90b1bd0e84"}
```

时间编码：月度 `YYYYMM` + 后缀 `MM`（如 `202608MM`），范围用 `Start-End`。

## 工作流

### 首次（建立本地基线，只做一次）

```bash
# 直接用包内自带基线打底 —— 几秒完成，不发任何网络请求
python scripts/ppi_baseline.py --build

# 仅当包内基线缺你要的指标、或需要比 2026-08 更新的历史时才走全量：
#   python scripts/nbs_ppi.py --list         # 先看计划（顺带刷新 cid 缓存）
#   python scripts/nbs_ppi.py                # 全量抓取，约 1~2 分钟
#   python scripts/ppi_baseline.py --build   # 重新固化
```

### 日常（每月）

```bash
# 1. 增量抓取最近 6 期（约 21 秒；自动复用 cid 缓存，跳过目录树遍历）
python scripts/nbs_ppi.py --recent 6

# 2. 合并进基线（同时报告 NBS 有没有修正历史值）
python scripts/ppi_baseline.py --merge

# 3. 核实（自动读「基线+增量」，与底稿逐列逐月比对）
python scripts/verify_ppi.py

# 4. 预览补充（openpyxl 输出到 _out/ 副本，先看效果）
python scripts/fill_ppi.py

# 5. 落到原底稿（COM/WPS 写入，保证格式，自动备份）
python scripts/apply_ppi_to_draft.py --dry-run    # 先看计划
python scripts/apply_ppi_to_draft.py              # 备份后直接写原底稿
```

### 常用参数

| 参数 | 作用 |
|---|---|
| `nbs_ppi.py --recent N` | 只抓最近 N 期（含当月），自动启用 cid 缓存 |
| `nbs_ppi.py --since YYYYMM` | 从指定月份抓起 |
| `nbs_ppi.py --use-plan` | 强制复用 cid/indicatorId 缓存 |
| `nbs_ppi.py --list` | 只列计划不取数（顺带刷新缓存） |
| `ppi_baseline.py --status` | 查看基线状态（有哪些期、最新期） |
| `apply_ppi_to_draft.py --dry-run` | 只输出写入计划，不动文件 |
| `apply_ppi_to_draft.py --json <文件>` | 指定数据源，跳过「基线+增量」合并 |

环境变量：`FA_WORKSPACE`（工作目录）、`FA_DRAFT`（底稿路径）、
`FA_BASELINE`（基线路径，默认 `<工作目录>/data/ppi_baseline.json`）。

> **cid/indicatorId 缓存在** `_out/nbs_ppi_plan.json`（35 条，含各分片 sdate/edate）。
> 增量筛选靠它判断"哪些分片覆盖目标月份"。若 NBS 新增分片导致缓存失效，
> 表现为**全部取数为空**，删掉该文件重跑即可（脚本会提示）。

**`fill_ppi.py` 与 `apply_ppi_to_draft.py` 的分工**：`fill_ppi.py` 用 openpyxl，快，
但保存会清空全表公式的缓存值，所以只用于输出副本预览；`apply_ppi_to_draft.py`
走 COM（WPS 原生），公式缓存值、名称定义、图片、批注、Table 全部原样保留，
**写原底稿必须用它**。

> 若只想「补最新那几期」，日常流程可精简为：`nbs_ppi.py --recent 6` →
> `apply_ppi_to_draft.py`（写入器会自动合并基线与增量，不必先手工 merge）。

## 写入格式要求（老板口径）

补进去的值必须是 **宋体 10 号、数值型、保留两位小数**。
`apply_ppi_to_draft.py` 逐格落实：

1. **数值**——写 `float(val)`，不是字符串（文本型会导致后续计算失效）
2. **字体**——`Font.Name = '宋体'`、`Font.Size = 10`
3. **数字格式**——沿用该格现有格式；若不含 `0.00` 才补默认
   （L 列 `###,###,###,###,##0.00`、M 列 `#,##0.00_ `）

实测本底稿 L/M 列的空白格**本就带好这三项**，所以脚本报告"修正字体 0 处、
修正数字格式 0 处"是正常结果——脚本是**兜底**，底稿没坏就不动。

### 新增未来月份行

底稿数据区 R4~R372，**R373 之后没有预留行**（默认 Times New Roman 12）。
下月数据发布后须新增行：

- 用 `Rows(last).Copy()` + `PasteSpecial(Paste=-4122)` 只复制**格式**
- 补 A/B/C 三列：月末日期 `date(y, m, 月末)` / 年 / 月
- 脚本已自动处理，本月底稿恰好到 2026-08，所以本次未触发

> A 列存的是**月末日期**（如 `2026-08-31`），不是月初。

## 指标口径（易错，务必核对）

| 底稿列 | 底稿表头 | NBS 指标来源 |
|---|---|---|
| D | PPI:家具制造业:当月同比 | 分行业→家具制造业 |
| E | PPI:文教、工美、体育和娱乐用品制造业 | 分行业→同名 |
| **F** | **PPI:塑料制品:当月同比** | **中类→橡胶和塑料制品业→「塑料制品业」** |
| G | PPI:通用设备制造业 | 分行业→同名 |
| H | PPI:专用设备制造业 | 分行业→同名 |
| I | PPI:电气机械及器材制造业 | 分行业→电气机械和器材制造业 |
| J | PPI:通信设备、计算机及其他电子设备制造业 | 分行业→计算机、通信和其他电子设备制造业 |
| K | PPI:仪器仪表制造业 | 分行业→同名 |
| L | 中国:PPI:汽车整车制造 | 中类→汽车制造业→汽车整车制造 |
| M | 中国:PPI:汽车车身、挂车制造 | 中类→汽车车身、挂车制造 |

> ⚠️ **F 列是最容易取错的**：分行业目录下只有大类「橡胶和塑料制品业」，
> 而底稿用的是中类细分「塑料制品业」。实测两者差 **0.8~1.0**，
> 取错会让塑料制品的价格指数整条偏移。
> 正确位置：中类「橡胶和塑料制品业」节点下的第二个子指标。
> 判定技巧：取中类「塑料制品业」后与底稿比对，**实测 104 个点全部一致（平均绝对差 0.000）**。

## 核实时的判断标准

`verify_ppi.py` 会输出三类结果，**处理方式不同**：

1. **完全一致** → 无需处理
2. **差异 ≤0.05** → **精度差异，不要改**。底稿 D~K 列存 2 位小数（如 `101.23`），
   NBS 官网发布 1 位小数（`101.2`）。底稿更精细，覆盖会降低精度。
3. **差异 >0.1** → **口径错误**，要查指标取对了没有（典型就是 F 列那种情况）

**补充策略是「只补不覆盖」**：只填底稿为空或为 0 的格子。

## 联网注意事项（重要）

> ⚠️ **别用 Content-Type 判断成败——这是本技能最大的坑。**
> 实测（2026-09-16）NBS **正常返回也标 `Content-Type: text/html`**，
> body 却是合法 JSON。曾据此误判为"被限流"，白等了十几分钟。

**唯一可靠判据是 body 能否 `json.loads`**：

| body 内容 | 含义 |
|---|---|
| 合法 JSON（`{"data":…}`） | ✅ 正常调用，即使 Content-Type 写着 `text/html` |
| `<html>… Please enable JavaScript …` | ❌ 触发 JS 人机验证（真限流） |

脚本里的 `parse_json(r)` 就干这件事，返回 `(对象, 状态描述)`。

- 脚本内置 `REQ_GAP = 1.2` 秒节流，**不要调小**
- 真限流后需等待较长时间（实测等 2 分钟仍被拦）
- **不要只看状态码**——限流时状态码仍是 200

## 边界

- 数据**仅供内部核价参考**，正式报告引用需注明来源与取数日期
- **本地基线 `data/ppi_baseline.json` 是长期资产，勿删**——它同时是「已有数据」的存档
- **包内基线含建立时的底稿快照**（`draft_snapshot`），那是原项目的记录。
  换项目后请重新 `--build`，否则 `--status` 里显示的底稿期范围是旧项目的、会误导
- **底稿早期数据无法核实**——两边起点不同，程序只核实重叠区间：

  | 列 | 底稿起点 | NBS 序列起点 |
  |---|---|---|
  | D/E/F/I/J/K | 1995~1996 | 2007-01（D/F/I）· 2014-01（E/J/K） |
  | G/H | 2002-04 | 2007-01 |
  | L/M | 2014-01 | 2014-01 |

  **不要用本技能的数据去覆盖底稿 2007 年之前那一段**（口径不同）
- 抓取依赖公网可达 `data.stats.gov.cn`；被限流时定时任务会失败，
  脚本会重试 4 次并给出明确提示，但不会自动长时间等待
